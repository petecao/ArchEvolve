# 06 — Which papers are closest to ours?

Created: 2026-10-09 14:17 ET
**Ticket:** [`../issues/06-closest-prior-work.md`](../issues/06-closest-prior-work.md)
**Method:** scoped narrative literature review (not a systematic review). Searched 2023–2026 on
2026-10-09. Every cited paper was opened at its arXiv, venue or DOI page. Read scope per source is
listed under [Sources](#sources).

## TL;DR

- **The gap is real but narrow.** No paper found formally verifies LLM-written, source-level
  performance rewrites of C/C++ against **reusable rewrite contracts proven once**. None formally
  verifies an **LLM-written accelerator offload**. But every *piece* has precedent, so the paper
  claims the combination and the new subject, never "first to verify LLM rewrites".
- **Closest three:**
  1. **Trivet** (arXiv 2026): when Alive2 times out or can only check within bounds, an LLM writes
     Lean proofs, with a gate that rejects `sorry`/`admit`, extra axioms and changed statements.
     It checks compiler transformations, not LLM rewrites. Integer IR only, no memory.
  2. **LLMLift** (NeurIPS 2024): the LLM writes the target program *and* the loop invariants, and
     an SMT solver checks them. Proofs are per program, for side-effect-free code lifted into a DSL.
  3. **ProofWright** (arXiv 2025/26): an LLM annotates LLM-written CUDA kernels for VerCors and
     Rocq. The LLM also writes the specification. Full equivalence for 14% of KernelBench L1
     kernels.
- **"Prove once" exists only for compiler IR peephole rules** (Alive, LPG, Hydra). LPG hit our
  exact risk: Alive2 cannot check a rule for all bitwidths, so it checks each width up to 64 bits.
- **Accelerator offload is the least crowded part.** Every LLM accelerator-code system found
  (Autocomp, KernelCraft, QiMeng-Xpiler) relies on tests. Formal accelerator interfaces (3LA/ILA,
  Exo) exist, but with no LLM involved.
- **Positioning in one sentence:** prior systems either verify each LLM rewrite from scratch at
  IR level and within bounds (LLM-Vectorizer, CoV), or let an LLM write per-program proofs for
  compiler or lifting tasks (Trivet, LLMLift, ProofWright). We prove each rewrite contract once,
  check each candidate artifact's change against the contract it applies, and let the LLM add
  only proof hints. Our subject is memory-bound C++ and its offload to a data-access accelerator
  (DX100).

## Detail by cluster

### A. The proof-hint half: Trivet, LLMLift, ProofWright

- **Trivet is the nearest precedent for "LLM helps when the formal verifier stalls".** Its
  motivation lists Alive2's three limits: solver scalability (timeouts), fixed bitwidths, and
  bounded loop unrolling. A deterministic, non-LLM generator writes the refinement theorem and a
  proof scaffold. The LLM only fills typed holes. A proof is accepted when it passes the Lean
  kernel, contains no `sorry` or `admit`, uses only standard axioms, and leaves the definitions and
  theorem unchanged. The scaffolding enabled 26 more proofs and cut mean proof time by 75.9%.
  - Difference from us: Trivet validates compiler transformations someone else wrote, in integer
    IR with no memory. Its loop support is "preliminary". Our subject is LLM-written C++ with
    arrays, indirection and accelerator commands, checked against a rewrite contract.
- **LLMLift**: the LLM writes a program summary in a Python IR plus loop invariants, and cvc5/Z3
  checks equivalence. If no invariant verifies, LLMLift "assumes that the PS itself is incorrect"
  and moves on. These invariants are proof hints in our sense, but nothing stops a bad invariant
  from being trusted unless the solver rejects it. No guard against assumptions is described.
- **ProofWright**: agents write VerCors contracts, loop invariants, assertions and frame
  statements, plus Rocq specifications and proofs. The authors rely on the verifiers for soundness
  ("we will never verify a program that is incorrect"). They concede that the LLM-based lowering
  from Rocq to VerCors annotations is not guaranteed correct, and that the contracts are inferred
  by the LLM.
  - Difference from us: the specification is fixed and proven once, and the LLM may add only
    proof hints, never specifications.

### B. "Prove once": peephole rules and verified rule libraries

- **Alive** (PLDI 2015, already cited by Extensa) is the classic: prove a peephole rule once, then
  use it everywhere.
- **Hydra** (OOPSLA 2024) generalizes peephole optimizations by program synthesis, without an LLM.
- **LPG** (2026) uses an LLM for the same goal and checks every bitwidth instance up to 64 bits.
  It says outright that a generalized rule cannot be verified over arbitrary bitwidths.
  - Lesson: "proven once" depends on what the verifier's logic can quantify over.
- **Paraskevopoulou 2026** (PACMPL, experience report): Claude Code produced a Rocq proof of
  semantic preservation for CertiCoq's ANF pass, about 7,800 lines in about 96 hours of guided
  work. Evidence that an agent can help prove a rewrite rule once; not a performance system.
- **Exo / Exo 2 / ATL** (already cited by Extensa): every scheduling step is a rewrite that
  preserves meaning, and Exo's rewrites double as instruction selection for accelerators. These
  systems are correct by construction, but code must first be rewritten into their language, and
  no LLM is involved.
- **Agentic MLIR** (LLVM Dev Meeting 2025 slides, gray literature): an LLM plans polyhedral
  transform sequences, and dependence analysis checks legality. Generated-code correctness is
  tested, not proven.

### C. LLM rewrites checked at IR level (CPU)

- LLM-Vectorizer, CoV, VecTrans, LLM-VeriOpt, and Singh et al. 2026 ("Verified Learning for
  Compiler Optimization") all wrap LLM output in **Alive2**.
- All five inherit Alive2's bounds. LLM-Vectorizer needed tricks to make Alive2 finish: aligned
  unrolling, C-level unrolling, assumed non-aliasing, splitting by vector lane. 31 of 149 cases
  still stayed inconclusive.
- CoV covers inconclusive cases with runtime checks. **None asks an LLM for proof hints, and none
  checks against a reusable spec.**

### D. GPU and tensor equivalence

- VOLTA (OOPSLA 2026), the Tensor Algebra Equivalence Checker (ARRAY 2026) and ProofWright
  verify **LLM-written GPU kernels**.
- They show that formal checks find bugs tests miss: 2 bugs in kernels that passed numerical tests
  (Tensor Algebra Equivalence Checker); "subtle correctness errors missed by conventional testing"
  (ProofWright).

### E. Accelerators

- **Tests only, with an LLM:**
  - Autocomp compiles and runs each candidate "against our functional test suite", comparing
    with a reference implementation (Gemmini, Trainium, L40S).
  - KernelCraft uses compile checks, simulation, and comparison with ground truth.
  - QiMeng-Xpiler uses LLM passes plus small SMT-based repair, with ~95% reported translation
    accuracy.
- **Formal, without an LLM:**
  - 3LA (TODAES 2024) uses a formal instruction-level abstraction (ILA) as the software/hardware
    interface, but validates whole applications by simulation.
  - Tenspiler verifies the lifting step and trusts the pattern-matching lowering to Gemmini.
- **No paper found formally verifies an accelerator offload written by an LLM.** Ticket 05 covers
  how verifiers model command interfaces.

### F. Testing-only performance agents (Extensa's neighbors)

- SuperCoder: 95.0% "correctness" by test pass rate.
- LOOPRAG (ASPLOS 2026): "mutation, coverage and differential testing".
- SeGaBench (2026): validators plus oracle artifacts.
- Also KernelBench and robust-kbench (both already cited by Extensa).
- All of these sit at the certified level, at most.

### G. Why the LLM cannot be the checker

- EquiBench (EMNLP 2025): across 2,400 program pairs and 19 LLMs, the best accuracies in the
  hardest categories are "63.8% and 76.2%, only modestly above the 50% random baseline".
- This supports keeping the formal verifier, not the rewrite provider, as the judge.

## Findings that touch ticket 01 decisions

1. **Decision 8 (hints never assume) is not new as an idea.** Trivet already enforces the same gate
   in Lean: no `sorry`/`admit`, standard axioms only, definitions and theorem unchanged. Cite it.
   Our contribution is that gate for C/C++ verifiers, whose escape hatches differ
   (`__CPROVER_assume`, harness edits, weakened contracts). Against ProofWright, our stricter
   split is a real difference: the LLM never writes the contract.
2. **Decision 2a ("proven once") may hit LPG's wall.** If the contract-level proof uses a bounded
   verifier, "proven once" quietly becomes "proven once within bounds".
   - Suggest ticket 10 applies the two proven levels to rewrite contracts as well, not only to
     candidate artifacts.
   - It should also name which verifier can quantify over array sizes and index maps.
3. **Decision 2c (bugs as motivation):** "formal checks find bugs testing missed" is already shown
   for GPU kernels. Our evidence must be specific: an expert's accelerator offload (`TDStepMAA`
   wrong-tile wait) that tests passed.
4. **"Why this attempt differs" (map):** the best published results are low.
   - LLM-Vectorizer verified 38.2% with heavy tricks. ProofWright proved full equivalence for 14%.
     Trivet's loop support is one canonical loop shape.
   - Trivet's gain came from a **deterministic scaffold** that leaves the LLM small holes. A proven
     rewrite contract could supply that scaffold for every candidate artifact that applies it.
     That would be a concrete answer to "what changes the outcome". Input for ticket 13.
5. **Related-work update from Extensa:** VOLTA (arXiv 2511.12638) was left out of the Extensa
   bibliography for lack of a venue. It is now OOPSLA 2026 (PACMPL, DOI 10.1145/3839470).

## Suggested baselines that mirror the closest work

These line up with the map's "Not yet specified → Evaluation plan":

- **Verifier without hints:** LLM-Vectorizer / CoV style. Verify each candidate from scratch; on a
  stall, report inconclusive.
- **Hints without contracts:** LLMLift / ProofWright style. The LLM writes hints *and* the
  per-candidate specification.
- **Testing-only certification:** Extensa, Autocomp style.

## Open questions

- **Guided Tensor Lifting** (PLDI 2025): only the abstract was read, so its checking method
  (tests, bounded or full) is unconfirmed.
- **VecTrans:** its "hybrid validation mechanism at the IR level" is not detailed in the abstract.
- **Reviewer risk:** someone may ask "why not let the LLM pick Exo-style primitives that preserve
  meaning by construction?" The paper needs one sentence on this. A likely answer: our rewrite
  contracts play the role of verified primitives, but over existing C++ and accelerator command
  code, with no rewrite into a DSL first.
- **Unseen work:** industrial work (GPU vendors, cloud accelerator teams) may verify LLM offloads
  without publishing it. Nothing was found.
