# Ticket 16: blind Extensa pairing

Created: 2026-10-06 ET. Scope: native and gem5 Extensa campaign orchestration.
Parent owns mbit10 leases, remote runs, source synchronization and prospective
population/statistical policy. This runbook launches no evaluations itself.

Every enabled campaign saves an immutable `paired_estimate` before entering each
outcome-bearing evaluator route. It freezes the portable Python implementation
bundle before setup and refuses implementation/configuration drift on resume.
Selection, confidence gates, certification priority and plateau accounting still
use the existing timing policy. The estimate ledger contributes no selection score.

## Evidence boundary

The current real-target adapter saves **structural unknowns**. `seconds: null` and
`eligible_for_agreement: false` are deliberate: no verified exact-registered-input,
complete-call native or MMIO count adapter is registered here. Registered SG hashes
and canonical adjacency identity are retained; equal vertex/arc totals are never a
count/input binding. Existing functional `gapbs.trial_lambda.v1` observations do not
prove either `bfs.complete_call.v1` or the gem5 MMIO backend. A functional source-view
or numerical rate change cannot silently supply that correspondence.

Every real forecast lists missing exact input/count binding, counted backend/build/
runtime correspondence, complete required mechanisms/composition, and prospective
freshness. Gem5 also names the functional trial-lambda to MMIO complete-call bridge.
No missing mechanism is zeroed, and none of these records can pad the twenty
application agreement pairs. A later verified adapter requires a separately tested
source/configuration/count bridge and a prospectively frozen model before timing.

Only `--fixture` accepts the optional synthetic `estimate_fixture` premise:
`work_units: {baseline: 10, candidate: 1000}`, `units_per_second: 100`. These produce
0.1 and 10 synthetic seconds. They stay `contract_fixture`, research-mode and
ineligible even when fixture timings select a gain. They are orchestration evidence.

## Stored identities and boundaries

The campaign store retains `records/paired_estimates/*.yaml`. Each record binds:

- Extensa campaign/mode, estimated basis, research estimator version/bundle hash;
- immutable payload identity, UTC estimate time and frozen policy hash;
- actual source artifact hash and subject ID;
- registered workload identity, canonical adjacency and representation hashes;
- selected representation/source/trial, target/ROI/thread/repetition configuration;
- frozen compiler/build/instrumentation/runtime and backend facts supplied by the
  real adapter before execution.

`pairing/policy.json` is immutable during a campaign. `pairing/outcome-accesses.jsonl`
is append-only and fsynced before evaluator entry. Every boundary cites its prior
estimate IDs and retains the actual requested subject/input/execution contexts.
Campaign summaries embed both the immutable records and boundary ledger, so copied
summaries can validate hashes, request correspondence and chronology without raw
performance files. Historical summaries lacking the optional ledger still validate.

The native adapter freezes all relevant baseline/role/class requests before A/A
pilots and both sides before each paired block. The gem5 adapter freezes all baseline
class requests before the first shared-baseline timing, then candidate primary and
diagnostic companion contexts plus every main class context before the first
companion outcome. `--baselines-only`, normal runs and resume use the same boundary.

A record name cannot make previously timed source content fresh. Identical source
artifacts reuse their already-frozen **unknown** forecast when the complete requested
input/build/backend/policy matches. Guest build record/output names may differ only
when pinned executable bytes and compiler/version/flags/adapter facts match. Actual
IDs and output paths remain in boundary contexts. Any other field, including an
unknown extra field, remains part of request identity. This is forecast aliasing,
not count-policy rebinding or a functional/MMIO observation bridge.

Different source, binary, input, role, diagnostic flags, compiler/runtime, backend
or configuration creates a distinct structural unknown. Known prior artifact access
is disclosed from retained evaluation identity/access metadata, without importing
any duration or ratio. The audit is conservative and incomplete for unindexed raw
history; it never certifies a new tuple as prospectively fresh. Prior companion
inputs, class aliases, historical artifacts and shared baseline tuples must all be
considered by the parent's prospective population audit.
