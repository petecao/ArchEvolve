## Verdict

Three mapping/admission gaps require correction before claiming a complete first-pair source inventory. They do not establish an impossibility of the trusted immutable-heap route, and they do not prevent a separately labeled partial import-syntax experiment. A fixed reviewed-source map is sufficient here: no general compiler construction or external source/VC soundness theorem is required.

1. **Allocator address/freshness interpretation is incomplete.** `well_formed` constrains allocation identity history/liveness/extent but does not relate numerical addresses of live objects. `allocate(h,n,a)` accepts arbitrary a, including the address of an already-live receiver. If numerical_address is meant to represent C addresses, fresh identity alone does not establish the original allocator's nonoverlap/fresh-memory relation. Supply uniform available-address/separation semantics as an explicit trusted allocator output condition, discharged under the existing allocation-success policy rather than added to original caller requires. Alternatively mark addresses as auxiliary uninterpreted labels and limit address-reuse/physical-layout claims; that would leave the full original address mapping pending. Include zero-size address/identity interpretation explicitly; permission and endpoint formation are already correctly distinct.
2. **The closed original-source gate is missing.** `prepare` rebuilds current model text and hashes it, and `check` repeats that same current construction. Listed source needles need only occur somewhere; no reviewed baseline hash/complete closed shape prevents an added extra write, branch or call from receiving the old VC inventory. A changed model file plus freshly prepared matching hashes would pass this checker while unmatched events remained. Pin the exact reviewed source/model text or complete source shape, and bind an exhaustive event inventory to those bytes. This is a narrow closed-source guard, not a demand for a generic AST compiler. Full-source hashes supporting future changed methods are provenance, not evidence that unchanged hand-written VCs cover new events.
3. **Complete-source/RTE/composition claims exceed the recorded map.** Local prefix establishment/step/exit VCs are appropriate, but receiver field/capacity/final-store access checks and source-event/frame induction links should be explicit mapped goals, not inferred solely from C1/C4 labels. `reads`/`writes` currently express logical range/liveness while generic caller operations are not translated by this prototype. Mark unsupported composition as refused/pending, retain exact representation premises and their origin, and do not publish pending_source_inventory=[] merely because every review-group string appears. The omitted-store/wrong-release controls should map their exact recorded mutated event sequences to the corresponding failed original obligation; handwritten detached formulas plus mutation metadata need an explicit checked relation. The four negative formulas are sensible mathematical countercontrols, but are not yet independently validated source-mutant VC generation.

The author acknowledged these corrections before any formal freeze; the initial32-target draft is not a final admission candidate. Re-review changed bytes separately instead of replacing this history.

## Parts that map well

- Mathematical next/issued identities are unbounded, retain previously issued dead identities, and avoid a machine-width epoch or finite allocation pool. Allocation resets new initialization bits rather than assuming a filled buffer. Release changes liveness without alias rewriting or receiver field reset.
- Constructor transitions follow the three initial stores, n==0 return, allocation, capacity assignment, prefix stores and final size store. No completed-fill result is an imported axiom. Prefix establishment/step/exit are legitimate Hoare-style obligations with an inductive invariant; dependencies=[] does not by itself make those hypotheses circular.
- Fresh allocation identity differs from a live receiver under well_formed; b!=r protects the constructor's field/buffer separation. Frame predicates preserve old live objects outside receiver storage and permit writes to genuinely fresh storage. A coupled invariant/certificate must carry freshness relative to the original heap through composition.
- Destructor has the right original precondition shape, null release, base-freeability, invalidation through all offsets of the released identity, content-frame versus lifetime-frame distinction and receiver-overlap control. Its post uses prestate data identity with poststate invalidity. It does not claim a valid/reset receiver afterward.
- The machine numeric kernel uses the correct int count bound4611686018427387903 for x86_64, explicit layout assertions, multiplication/index/increment/variant checks. Its auxiliary k<n premise must be connected to the actual loop-state relation; it is not an original caller precondition.
- Source-specific claims are emitted as separate top-level check lemma targets outside imported semantics. The functional map theory contains definitions rather than source-specific desired-result axioms. Actual Why3 syntax/import closure and solver/dependency audit are still unvalidated; this review does not certify them.

## Remaining semantic boundaries to keep explicit

The first map is int-only, with 4-byte elements and 24-byte receiver layout. Typed-cell memory at field/element start offsets is an abstraction, not yet a generic byte/cast/unaligned/partial-write semantics. Original valid(this) must map through a precise typed layout relation; no hidden alias/separation premise is allowed. Source C scalar input initialization and numeric-kernel representation premises need recorded origins. A complete capability demonstration must prove the mapped source targets and enforce their inventory/dependency closure; proving primitive heap identities alone cannot be called original constructor/destructor acceptance.
