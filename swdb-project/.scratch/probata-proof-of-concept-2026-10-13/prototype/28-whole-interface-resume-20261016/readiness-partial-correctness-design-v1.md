# Ready-until1: partial correctness without fairness

2026-10-16 ET. Prospective design, no implementation/admission/proof result. Root selected WP partial correctness as the preferred first route; the finite same-thread source profiles remain priority.

The pinned original interface exposes blocking `wait_ready`; it has no source `get_tile_ready` declaration. The concrete model has an explicitly logical query `dxc_get_tile_ready`: while counted commands are pending it may return0 or1;1 performs the same covering wait, and0 grants no readiness. Any source fixture query must therefore be a separately pinned synthetic query/event, never passed off as an original header call.

`while (!ready(tile)) {}` may execute0 forever under that semantics. Its desired property is safe access on normal loop exit, independent of whether an exit occurs. No eventual1/fairness premise, false source requires, dropped unwinding goal or hidden choice restriction is allowed. A finite-budget native trace that samples1 is a health/normal-exit control, not evidence that all executions terminate. Infinite0 behavior remains permitted.

The preferred prospective WP route needs an exact source-bound loop invariant distinguishing pending versus covered, exact query call/covered-state relation, and an explicit `terminates \false` partial-correctness clause. That clause removes a termination requirement; it must not become an assumption that the function cannot return. Normal exit with answer1 supplies the existing covering-wait rule. All ordinary RTE, initializedness, frame and source-to-value obligations and healthy nonvacuous smoke controls remain mandatory. The current checked-body renderer rejects generic WP summary fallback; this design requires a separate exact reviewed source/query policy and cannot bypass that refusal. No new hardware-body theorem is required: the existing explicit MMIO-implements-call-semantics premise remains the intended TCB.

A possible later CBMC alternative is checked loop-contract induction. The primary [CBMC loop-invariant documentation](https://diffblue.github.io/cbmc/contracts-loop-invariants.html) describes base/induction obligations, and the [loop-contract manual](https://diffblue.github.io/cbmc/contracts-loops.html) describes its goto-instrument pass. This is research context, not an attested capability of the selected6.11 runtime: exact version source, goto-instrument bytes/closure, invariant/assigns and all generated checks would need their own prospective method and admission. The existing CBMC method/lineup and unwinding checks remain unchanged.

Next implementation seam after finite source acceptance: a fixed synthetic source-owned event Plan carrying literal thread switches, CPU CAS and logical ready query positions over the same concrete model. Ticket28 explicitly permits fixed sequential thread-ID order; actual interleavings remain46/47. Every event/prototype, source span, typed pointer/cell mapping, ownership/history effect and source-preserving native view must be closed and recorded under the same new semantics entry. Existing abstract25 evidence remains separate.
