# Initialized int embedding: semantic boundary review

Date: 2026-10-16 ET. Read-only review of the uncommitted heap_reallocation.mlw / vector_reallocation_vcs.py boundary. No compiler, verifier, prover, test, tool probe, remote connection or repository edit was performed.

**Recommendation: retain int32_region as a definitional source-image/typed-memory relation, but make its qualification explicit. Do not claim that existing Heap.well_formed + old t25_repr, or the raw v3 C precondition by itself, entails it.** The current explicitly unsupported preparation may continue. Actual admission needs either a pinned, scoped WP-Typed-to-Heap projection with checked caller/source coverage, or a separately explicit qualified typed-object domain whose entry is discharged at each caller. A comment saying “source int-object embedding” is not that correspondence argument.

## Three distinct statements

1. **Custom heap entailment is false.** In the present theory, well_formed constrains allocation IDs, addresses, extents and separation; typed_reads checks liveness/bounds/alignment. Neither fixes a cell's constructor. An otherwise eligible vector can have an initialized Pointer cell at its first readable backing offset. Old t25_repr holds while int32_region fails. Likewise an initialized Integer outside signed32 bounds is permitted by the old abstract predicates. Do not add a global initialized=>Integer law: initialized pointer fields are legitimate. Grow.copy.read now proves a consequence of the stronger t25v3_eligible premise, not the missing entry bridge.

2. **A WP Typed projection can legitimately supply the relation.** Installed MemTyped.ml represents integer, pointer and float values in separate chunks. Lines964-975 construct integer-chunk well-formedness with Cint.range; line996 reads an integer from M_int, while line998 reads a pointer from M_pointer. Consequently, for the selected machine-int Typed semantics, a projection of the int chunk to Heap.Integer cells can preserve arbitrary bounded integer loads without adding a C caller requires. This is a semantics correspondence, not an axiom proving a desired grow result. Declare its exact source domain, initialization/bounds/alignment mapping, type-chunk selection, frame preservation and actual machine-int configuration, and pin the translator/foundation. Do not justify it from a purported universal Pointer-tag exclusion or general source T=int alone. WP's manual describes separated value-type memories and restrictions on heterogeneous accesses; it does not turn this into a raw-C effective-type theorem. [WP manual](https://www.frama-c.com/download/frama-c-wp-manual.pdf), sections1.4/3.7; [installed Model API semantics](https://www.frama-c.com/api/frama-c-wp/Wp/Memory/module-type-Model/index.html).

3. **The existing raw C contract does not prove effective-type safety.** std_vector_int_valid requires bounds/initialization/size/capacity, and v3 additionally requires freeability and different allocation bases. It has no effective-type/history clause. On the selected target, allocate eight suitably aligned bytes, store a void* value through a void** into that allocation, and construct a separate stack receiver with data=(int*)allocation, size1, capacity2. The bytes are initialized, the allocation is live/freeable and receiver/backing bases differ. Yet an int load of that stored pointer object violates C effective-type access rules. A float-written allocation gives the same issue. This is a source-level boundary example, not an executed diagnostic or a claim that the malformed state is a valid C++ vector<int>. C11 draft6.5p6-p7 specifies effective types of allocated storage and allowed accessing lvalue types. [N1570](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf), section6.5. ACSL treats memory validity, initialization and well-typedness separately; the reviewed implementation manual's well-typedness subsection supplies valid_function, not a general effective-type predicate for int objects. [ACSL reference](https://www.frama-c.com/download/acsl.pdf), sections2.7-2.8. Do not invent an unsupported typed-object ACSL primitive or use an int read in a premise as proof that this read was legal.

## Minimal sound path for this project

For the narrow actual constructor→reserve/grow→guarded read→dtor source vertical, derive the typed region from the real constructor's typed int stores, source int parameter range and initialization/access obligations. Preserve it through exact admitted calls and source frames. The old buffer may contain arbitrary different int values; no uniform-seven assumption enters standalone grow. Unused capacity need not be initialized. This gives a checked source-local entry fact without adding n-dependent caller premises or requiring exclusive ownership. Retain unrelated live objects, issued dead IDs and escaped aliases.

For standalone grow/reserve model records over arbitrary incoming heaps, state the theorem domain precisely: arbitrary heaps **representable under the declared typed-int source/memory relation**, plus the actual v3 clauses. If the framework already admits only such typed-model executions, expose and pin that shared restriction and audit the projection; it need not become a new C requires. If the claim is instead all raw C states satisfying the current v3 clauses, the bridge is not justified: add an explicit new qualified typed-object/resource domain and prove its source admission, or broaden memory semantics to track effective types and prove/refute each evaluated load. Renaming the representation predicate without exposing this domain would silently strengthen the theorem's precondition.

The projection must also explain overlapping type views: WP has separate integer/pointer chunks, whereas this heap has one sum-valued cell at an offset. Either support only checked homogeneous typed-object accesses at represented offsets, with complete external/source-call admission, or extend the representation. A module containing no casts does not exclude an incompatible object supplied by an external caller. A source-derived vector<int> construction can establish the needed local relation; a free int* parameter or forged C struct cannot acquire it merely from its spelling. Preserve original v2 identity and negatives; do not relabel an excluded counterstate as proved safe or claim that the old public model contract was strengthened invisibly.

Pointer history should remain local and source-linked as proposed. Establish saved/data/new/automatic identities from actual declarations, stores, allocations and calls; do not introduce a broad pointer-map well-formedness premise over all arbitrary incoming heap cells. The typed projection itself grants no origin, exclusive owner, new liveness fact or alias refresh. Address reuse never restores a dead ID.
