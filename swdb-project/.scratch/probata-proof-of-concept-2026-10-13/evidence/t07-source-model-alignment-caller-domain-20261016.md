The language justification is limited and direct: objects must meet their type's alignment requirements; normal allocation returns suitably aligned storage, and a typed array new-expression creates array objects and yields the first element pointer. It does not promise scalar payload initialization. In-bounds typed element addresses then refer to actual T objects; alignment follows object identity rather than a guessed numerical address modulus.

## Caller states that typed declarations do not certify

CSRGraph constructors at131–142 accept already-created neighbor/index pointers, store them and immediately subtract index endpoints. They do not validate provenance, alignment or ranges. Its pointer fields are public at256–263; pvector start_ and queue pointer/counter fields are public as well. A well-typed Graph object can therefore contain pointer values whose referents have no established source array/lifetime/alignment history. A source entry must prove that history and bounds; merely naming the parameter Graph*, NodeID* or pvector does not do so.

The natural caller chain main→Builder::MakeGraph→DOBFS/DOBFSMAA→TDStep supplies candidate construction sites. It still needs a closed proof of selected builder path, valid graph data, no invalid public-pointer mutation, numeric representability, live storage and every accessed index. Serialized inputs and arbitrary external constructors require independent validation. This note has not discharged graph construction, the whole caller history or the source's OpenMP/device/runtime requirements.

## Concrete alternate source boundary: in-place building

CLI in_place_ defaults false (command_line39) but -m sets it true at103; Builder44–51 copies that selection and MakeGraphFromEL322–328 chooses the alternate path. MakeCSRInPlace206 reinterprets pvector<EdgePair<NodeID,NodeID>>::data as DestID*. At216 and252 it passes that storage to std::realloc, and CSRGraph later deletes the neighbor pointer as DestID[] (graph117/122). Source new EdgePair[] storage is not automatically a NodeID array object, even when its physical address is aligned for the contained NodeID members. Reinterpretation does not itself supply that array/lifetime/ownership theorem.

This is an unsupported/nonportable C++11 source-storage path for the proposed typed-array correspondence, with an allocation-family/lifetime concern that must be separately repaired or justified. It is not a misalignment counterexample by itself, and this review does not claim the actual helper run used -m. [N3337 C allocation library](https://timsong-cpp.github.io/cppwp/n3337/c.malloc) and [C11 draft7.22.3.5](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf) constrain realloc's allocation history; language-level array-object/lifetime compatibility is an additional issue. A compiler/runtime implementation convention cannot be silently treated as portable source semantics. Documenting actual -m absence is source-backed path selection, but cannot certify arbitrary MakeGraph callers or fix this branch globally.

## Hand-model accesses and exact WP boundary

The hand helper model dereferences metadata fields, atomic scalar targets, local/shared NodeID cells and pvector pointers; TD additionally dereferences Graph's neighbor field and neighbor/offset/parent arrays. The model's NodeID static local storage is itself a typed C array, so its own C-object alignment has a source basis. Mapping that block to source new[] remains a separate one-live-buffer/noescape/lifetime representation argument. In particular, static/global initializedness must not be used to infer that a fresh source new NodeID[] payload was initialized. The observed helper initializedness gaps and the Typed byte-offset conversion gap remain distinct from physical alignment.

Pinned MemTyped1042–1069 delegates validity to MemAddr allocated-range predicates. The shipped memaddr theory49–61 constrains base/offset/allocation bounds, not physical alignment congruence. wpRTE128–140 explicitly emits the unsupported alignment warning and sets pointer_alignment=false. Hence the all-goal helper result—even a future complete one—cannot be reported as checking those guards. Same-base/type validity in this abstraction is not the missing physical/source correspondence proof.

C++ Graph/reference/class fields are related to C stand-in fields by a proposed semantic mapping, not a demonstrated binary-layout reinterpretation. The source constructor/reference const/private rules, array cookies, object lifetime and target ABI are not proven by identical field names. Atomic/compiler/device instructions may also impose target/runtime obligations beyond ordinary scalar-object alignment; this note does not certify them.

## Minimum sound next correctness gate

Retain the exact warning and full-C-RTE=false. Establish a per-access provenance relation: the interface object is a live properly typed object; each pointer derives from a successful source typed array construction; bounds keep every evaluated endpoint/access within that same array; no invalidation/public mutation/escape breaks the relation. Prove this at the actual caller entry from its source producer chain, rather than assume alignment of every arbitrary incoming pointer.

For a restricted ordinary typed graph-builder path, validate actual CLI/path selection and graph-input/builder invariants. Keep in-place reuse and arbitrary external-pointer constructor states unsupported until separately handled. Record source-array element identity distinctly from allocation-base equality. The physical alignment subclaim can then be justified by C++ object construction within that restricted relation, while the remaining allocation/initialization/alias/caller/device conditions stay explicit. Without that closed relation, report alignment as unsupported rather than adding a premise or suppressing the warning. No source repair or new evaluation is authorized or launched by this note.
