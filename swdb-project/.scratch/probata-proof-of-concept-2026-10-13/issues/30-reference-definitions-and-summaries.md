**Time estimate:** about 1 week

**What to build:** Proofs of candidate artifacts stop re-proving DX100 building blocks. Each reference semantics the DX100 intrinsics use gets an ACSL logic definition, proven against the C lowering of the reference code. Against those definitions, each DX100 intrinsic gets a per-call summary (values plus hazard-state effects), proven once against its lowering under the proof semantics and kept as a summary proof record. Each summary's three generated forms (SAWScript, C stubs, ACSL) must give the same verdict, checked with 23's agreement check. Library entries whose text contradicts the proof semantics get new versions first: the completion assumptions of the 10 DX100 intrinsic entries, and `dxc_const_i32`'s result clauses. Old versions stay. An entry yields summaries only once it agrees. End to end: `swdb prove` on an intrinsic entry writes a summary proof record that later proofs of candidate artifacts pin; the same job on an old, contradicting version is refused.

## Acceptance

- [ ] **Reference definitions.** Every reference semantics the 10 DX100 intrinsic entries use has an ACSL logic definition in the logic library. Each has a proof record (subject kind: library summary; assumption below) showing it matches the C lowering of the reference code (which uses the `std::vector` model). Negative control: a planted off-by-one definition is refuted by the bounded verifier and never proven.
- [ ] **Per call, not per loop.** The range-loop summary describes one call with its continuation registers. The whole-loop range-loop reference no longer serves as a summary (map 16 item 9).
- [ ] **Summaries proven once.** Each per-call summary is written in the frame's `acsl` field against the definitions and carries hazard-state effects (which tiles and registers a call leaves uncovered, what a wait covers). Each has a summary proof record from `swdb prove`: subject the entry's summary, its level, and pins for the entry hash, the reference definition, the proof-semantics version, the method version and every build constant.
- [ ] **Summaries never claim too much.** Negative controls: a summary that says its output tile is ready without a wait, or gives a wrong continuation-register value, is refuted or left not proven. No counting record names it.
- [ ] **New entry versions** (map 12 item 10). New versions of the 10 entries' completion assumptions no longer contradict the proof semantics. Today's text says a wait does not cover a store through its source tile; gem5 shows it does. The new text says so, and that coverage does not follow a filled range loop's tile inputs. They can cite research 14 instead of "assumed, owner Eric". New versions of `dxc_const_i32`'s result clauses (the intrinsic's and its `dx100-mmio 1.0-e4fc4af` lowering's) no longer name the `constant_uncovered` control, which the gem5 rule accepts. `swdb validate` and `swdb build` accept every new version.
- [ ] **Old versions kept.** Old versions still validate with unchanged content hashes. Certification records that pin them still count for certification.
- [ ] **Only agreeing entries yield summaries.** `swdb prove` refuses a summary job on an old, contradicting entry version, with a named refusal. The same job on the new version runs.
- [ ] **Summaries feed the level.** Through `swdb candidate-level`: a fixture candidate artifact whose proof uses a summary proven only within bounds reads at most proven within bounds (cap rule). After that summary's entry hash changes, the candidate artifact's proof record stops counting.
- [ ] **One source, generated forms.** Each summary's SAWScript form (22's translator) and C-stub form (23's translator) are generated from its one ACSL source. No form is written by hand.
- [ ] **Three forms agree on every per-call `dxc_*` summary.** 23's agreement check runs SAW on the SAWScript form, the C-stub fallback on the C stubs and WP on the ACSL, over caller scenarios. Every safe caller proves in all three forms. Every buggy caller (for example, one that reads the output tile without a wait) is refuted by the SAWScript and C-stub forms and not proven by WP. The result is recorded per summary. Negative control: a hand-weakened generated form (one hazard-state effect dropped) fails the check and names the summary and the scenario.
