# Proof setup and fresh WP verdicts

Created: 2026-10-15 ET. Probata proof of concept ticket 36.

Every `swdb prove` job passes a setup preflight before the adapter runs. Each
WP, CBMC, crux-llvm, and whole-function CBMC proof checks its generated inputs
again immediately before its verifier subprocess starts. A refused setup stops
the batch, names the rule, and writes no record for that job.

`proof_setup_check` records the check version and content hash, method-version
pin, input `hashes` and individual generated-run checks. A job that returns an
unsupported-subset outcome without starting a verifier has a preflight result
and an empty `runs` list. A skipped job runs no check or verifier.

The checks are implemented by `swdb.proof_setup`. Their identity covers both
that Python module and the Frama-C inventory reader, `swdb/proof_report.ml`.
An execution method must pin both checks' versions and hashes under `checks`.
Historical `contract_fixture` method files keep their fixture status; they do
not establish execution evidence for the current checks.

## Frozen inputs

The preflight pins the contract and source translation unit. The final check
rechecks their contents and the method file, each summary pin, the generated
lowering, the final verifier input and the run plan. Each formal clause needs a
proof placement. Hazard probes must occur in the generator's lowering and in
the final verifier input; hint text cannot supply a missing generator probe.

Assumption statements in source code or a C lowering are refused. Bounded
harnesses have a separate, explicit provenance: their input-domain restrictions
come from bounds and the proof unit's declared preconditions; summary stubs
supply summary postconditions. These are the translator's generated bytes,
checked against the planned input, rather than hand-written harness premises.
A caller condition belongs in the contract and its lifting obligations. Adding
`assume(parent[v] >= -1)` to a harness does not make an undeclared premise legal.

WP always uses cache mode `none`, the x86_64 machine model, the frozen solver
lineup and budgets, smoke tests, and default warning levels. Existing sessions,
script/cache loading, property suppression and every `FRAMAC_WP*` environment
variable stop the batch. Only the freshly compiled inventory module may be
loaded, with its compiled bytes and source checked before invocation.

## Reading a fresh WP run

The verdict reader combines WP's per-goal JSON, its per-property CSV and a
same-process inventory of every generated obligation. The inventory enumerates
`Wp.Wpo` directly, including obligations WP omits from JSON when they are never
tried or automatically discharged. Directly discharged obligations require
actual valid prover results; missing, untried obligations remain not proven.

All generated goals and lemmas, call-site preconditions and termination goals
must pass. Each not-Valid property must have a classified failing goal. The
proof unit's own declared preconditions can have CSV status `Ignored`: they are
the conditions of its theorem, not call-site obligations. This exception never
covers an Unknown call-site property. Consolidated `[ Valid ]` output never
establishes a proof.

An `Extern` property is accepted only for the exact contract function in an
adapter-created allowlist backed by a pinned summary, once-proven C model, or
DX100 proof semantics. Each accepted property adds an assumption entry. Global
axioms, admitted lemmas and any other unexpected Extern stop the batch. The
inventory covers user includes as well as the generated input; declarations
shipped with the pinned Frama-C installation belong to its trusted-tool boundary.

The `smoke` field distinguishes reachability controls from proof goals. Every smoke test must have `passed: true`. A Valid raw proof of a smoke goal
means dead code, so it voids the proof with failure class `vacuous_pass`.
Timeouts and unknowns retain their failure classes and goal IDs for the proof
hint loop. Records retain `verdict_reading`, every classified unproven property,
and the fresh reports by external path and hash. No cached report is consulted.

## Verification

`tests/test_proof_setup.py` drives `swdb prove` for scripted setup failures and
real Frama-C controls. The real controls isolate hidden lemmas, failed call-site
preconditions, nontermination, admits, axioms, contradictory preconditions and
invariants, allowed summary Externs, false targets and never-tried goals. Real
runs use the shared verifier lock and the 8 GiB RSS watchdog.
