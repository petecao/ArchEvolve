## September 29 audit of revision 0.1.2

This catalog is a small, source-reviewed research prototype for asking concrete hardware questions. It contains six records: two DX100 editions, two Terminus configurations, Prodigy, and one SpZip mapping. It is not a hardware correctness certificate, performance ranking, or ready-made BFS accelerator. Every capability belongs to a named record and operation; families provide an index, never inherited capabilities. The [YAML](../catalog/hardware-v0.1.yaml) carries stable claims, exact locators, public URLs, source hashes, unresolved requirements and reference parameters.

The current data revision is `0.1.2`, deepening the first integration draft `0.1.0`. Its evidence is static paper/code inspection on September 29, 2026. No simulator, benchmark, architecture implementation or live virtualization work was performed. The original taxonomy and provisional seed were discovery leads; assertions below were checked against the primary documents or pinned source paths.

Operations additionally identify their realization as a native primitive, documented sequence, or mapping-specific role. Unknown/unsupported operations do not acquire a realization claim. ## DX100: two editions and two kinds of result

The [versioned paper](https://arxiv.org/abs/2505.23073v2), PDF pp.4–7, separates stream and indirect access. SLD loads constant-stride elements into scratchpad tiles; ILD uses tile indices to gather array elements. Feeding a gathered index tile into another ILD expresses chained indirection. RNG expands active half-open ranges into outer/inner index tiles, which subsequent accesses consume. A range gather is a composition, not a magical single instruction. Conventional random-base pointer chasing is explicitly outside §4.1; array-based chaining is different. Claims `dxp-read`, `dxp-interface` and `dxp-translation` delimit those assertions.

IST assigns indexed values, while IRMW accepts a restricted reordered class including add/min/max. The many ALU operators in §3.1 do not imply corresponding memory-update operations. Table 2 lists no IRMW result tile, so returned old values remain unknown for this paper edition. Neither the table nor the presence of atomic CPU baselines establishes a DX100 CAS instruction (`dxp-update`).

The [public artifact pinned at e4fc4af](https://github.com/arkhadem/DX100/tree/e4fc4afdf894f295442cef3604667a469fab8e62) is a separate authority. The API accepts an optional destination tile for scalar/vector stores and RMW. `IndirectAccessUnit::recvData` copies the current word into that tile before applying the update. Explicit typed execution branches implement add/min/max; the inspected indirect path has no CAS branch (`dxc-old`). This is observed source behavior, not a tested global atomic contract.

A concrete example explains why validity and order are fields. If two active entries update the same word from 10 with additions 1 and 2, the inspected single response-group path yields old values 10 and 11 when processed in that list order. This is a local source inference, conditional on the entries sharing that group/order. It does not establish all drain schedules or CPU participation. If the second entry is masked off and its old-result storage contains 92, the masked path may finish that slot while leaving 92 untouched. Reading it as a newly returned old value would be wrong. `dxc-mask` grounds this in `setFakeData`; `dxc-local-order` grounds list traversal and pending-line forwarding.

The artifact reads indirect indices and range bounds as uint32, while range continuation/stride registers use int. A 64-bit loaded payload therefore does not imply a 64-bit range/index ABI. Optional `type_constraints` encode the inspected six primitive payload types and 32-bit indirect indices separately. The observed BFS compositions list their int32 payload only; generic sequence compatibility is not inferred from every primitive type. Empty lists and absent constraints preserve unknown or inapplicable domains as explained by their notes. Requirements must establish representable, nonnegative indices/bounds, positive stride, correct sizes and continuation behavior (`dxc-gather`, `dxc-range`, `dxc-stream`). Independent review identified a further address-domain limit: `my_word_size` is int and `idx` is uint32_t. On the examined ABI, their product is 32-bit unsigned before the wider base is added. With base `0x100000000`, size 8 and index `0x20000000`, an isolated C++ expression produces the base instead of base plus 4 GiB. Thus every active index needs a representable byte-offset product, independently of index encoding: for positive 4/8-byte elements on that ABI, `word_size * index < 2^32`, plus normal base/range checks. The post-computation range check checks the computed address, so it cannot alone show a wrapped product still denotes the intended element. This is a source-expression limitation and pure host example, not a gem5 execution or runtime-validated hardware defect (`dxc-byte-offset-domain`).

The reference 16384-element tile is a SimObject default, not every run's actual configuration (`dxc-config`). Independently, SPD size storage and getSize/setSize use uint16, as does the API size read. Effective tile capacity and produced lengths need their own representability/allocation proof; an Unsigned knob is not a broad legal capacity domain. No new legal size range is asserted. Floating MIN/MAX use comparison-and-select expressions that choose the incoming operand when the comparison is false. Consequently NaN placement and signed-zero operand order can change results. The typed branch proves an operation exists; it does not prove a bitwise commutative numerical contract (`dxc-float-order`, explicitly an inference from source).

Completion is deliberately scoped. The paper says software waits before scratchpad consumption or accesses to updated global memory. In inspected artifact paths, accepted/replaced no-response writes feed counters; pending packet counts and modeled latency gate instruction finish and tile readiness. A callback named “received responses” is not necessarily an external write acknowledgement. The primary audit now resolves the ready response: `CpuSidePort.cc` L295–315 holds the mapped read until the tile-ready counter is zero and returns constant 1; `MAA.cc` L652–676 releases held responses. This is a held load followed by an API fence, whereas paper §4.1 describes polling (`dxc-ready-response`).

The audit also narrows the direct-write uncertainty. Reference `scripts/sim.py` selects Ramulator2; an accepted write calls `accessAndRespond`, which reaches `AbstractMemory::access` and updates backing storage when present and permitted. This occurs before DRAM timing completion. Thus a no-response write is not by itself evidence of lost data. This source path still does not prove the composition of every route, CPU ordering, coherence or observer visibility (`dxc-direct-backing`). The separate research worker first identified these paths; this catalog independently read the pinned primary ranges before incorporating them.

Readiness is also not a universal reuse barrier. The inspected counters cover explicit source/destination operands, while condition-only tile use participates in scoreboard checks but not those counter updates. A caller needs a completion barrier covering the actual consumer before overwriting its mask. This is a research-only missing mapping proof, not a claimed reproduced defect or reachable counter wrap (`dxc-reuse-scope`); no new hardware capability derives from it.

## Terminus: tasks, partitions and returned results

The [MICRO 2024 paper](https://doi.org/10.1109/MICRO61859.2024.00092), PDF pp.4–9, specifies Read, ReadRange, Write and task graphs for hash lookup/update and pointer traversal. The hash update replaces a found value and reports success. Fig.4's CAS returns success; it does not establish fetch-old. Generic add/min/max tasks are not promoted merely because a programmable ALU exists (`term-read`, `term-write`).

The serializer excludes conflicting tasks within a partition, while the ROB delivers completed task results in enqueue order. These are independent duties. Tasks changing partitions re-enqueue; local exclusion alone is insufficient across cores, where concurrent CLHT uses shared node locks. Core acquire is asynchronous: notification after running users drain, rather than instruction issuance, permits conflicting host work. Deferred operations retain their partition until handler response or completion/release (`term-order`, `term-host`).

The §VII-E configuration removes atomics and multiplication primitives and executes atomic/hash operations on the core. It deserves a separate configuration record because the execution location changes even when the application still performs CAS. The reference fabric/ROB/partition sizes in Table II remain fixed-reference values, not tuned recommendations (`term-deferred`, `term-config`).

## Prodigy and SpZip are different forms of assistance

[Prodigy](https://doi.org/10.1109/HPCA51647.2021.00061) communicates a DIG containing array bounds/sizes and traversal/trigger edges. It describes memory relationships rather than an offloaded program. Demand loads and prefetch fills drive nonbinding L1D requests through single-valued and ranged indirections, with PFHRs tracking sequences. Sequences can be discarded when the core catches up. CPU demand accesses and updates remain authoritative (`prod-dig`, `prod-prefetch`). The examined Edinburgh PDF has a cover page: PDF pages are one greater than manuscript pages. The selected reference has 16 PFHRs; the paper's sweep does not establish a runtime configuration API (`prod-config`).

[SpZip](https://people.csail.mit.edu/sanchez/papers/2021.spzip.isca.pdf) uses a DCL stream graph that can fetch and decompress data into queues. In the Push graph mapping, neighbor streams are supplied as values, but shared destination data requiring atomic updates is only prefetched. The CPU retains those atomic accesses (§III-D, PDF pp.8–9). This destination-specific restriction must not erase SpZip's real compressor writes or its ability to handle phase-separated read/write structures (`spzip-fetch`, `spzip-cpu-update`). Its publication is ISCA 2021; an older local filename incorrectly says MICRO.

## Applying this catalog to the received BFS profiles

The inspected pinned `TDStep` reads the frontier, CSR offsets and neighbors, reads `parent[v]`, performs CPU CAS, then explicitly stores the parent and appends successful discoveries. These are not one undifferentiated “indirect read.” Source `graph.h` defines SGOffset as int32_t; the received profiles report int64_t. Resolve the source revision/type binding before claiming a mapping (`bfs-types`). Neither average index jump nor reported within-page distance proves cache misses, TLB behavior or the superiority of a reorder buffer.

Read candidates can be explored for immutable graph arrays or phase-stable frontier ranges while CPU updates continue elsewhere. DX100's no-core-stores condition concerns its accessed memory regions during the offloaded loop; §3.6 specifically concerns indirect arrays within the ROI. It is not a prohibition on all system memory writes. Conversely, reading `parent` through DX100 while CPU CAS modifies `parent` cannot be declared legal just because the requested accelerator operation is a read. Exact arrays, aliases, phases and writers decide that question (`bfs-mapping-boundary`, a mapping inference). The existing `TDStepMAA` source provides concrete range/chained instruction compositions, but its accelerated parent sequence uses an OpenMP critical region plus masked store with old results; its fallback uses CPU CAS. This source example must not be relabeled as an engine CAS or treated as a supplied equivalence proof (`dxc-bfs-composition`).

The SpZip record describes a particular Push mapping. Its destination-prefetch role must not automatically bind to `VertexOffsets` or another unrelated array just because both use indirect addressing. Automatic BFS projection should keep it as a mapping reference unless the role and requirements are established; generic inspection can still expose the evidence. Likewise, retrieval of ranged/chained DX100 operations must show the required instruction sequence instead of suggesting a native primitive.

For Josh, a productive query sequence is: identify the required operation and result; retrieve matching record operations; check the representation and datatype/range widths; then resolve mapping requirements and observer completion. Gather queries may return conditional executors and prefetch assistance. A fetch-old add query has artifact evidence but not a paper-level result contract. A CAS executor query must distinguish Terminus with engine CAS from deferred Terminus, Prodigy and the selected SpZip mapping. None of those lookups constitutes a winner recommendation or a workload compatibility certificate.

## Review and portability

Catalog validation checks YAML/JSON-compatible types, required fields and references. Primary hashes bind examined editions; locators name PDF pages/sections or pinned code lines. Raw binaries stay outside Git. Prior reports helped locate evidence but are not sources for architecture claims. Unknown fields identify specific missing evidence rather than replacing known interfaces and operations. Root owns the general loader/tests, seed/default migration and integration; this change owns only the catalog and this evidence document.

## Audit limits and next questions

The catalog is deliberately incomplete: it does not enumerate every compute/reduction instruction, possible Terminus task, SpZip compressor mapping or private DX100 extension. Adding one requires its own source-backed operation/result/ordering/completion record. Next work should prove an exact BFS array/type/ROI binding, check each consumer-aware reuse barrier, and trace all-route observer visibility before any executable mapping. Numerical equivalence needs datatype-specific requirements, especially for reordered floating operations. None of these unresolved obligations can be discharged by a successful YAML parse.

The `0.1.2` audit validates six records, 32 operation entries, 35 claims and 23 hashed sources. All claims are referenced; 73 pinned code ranges pass file/line-bound checks; the four paper PDFs have 18, 14, 14 and 15 pages respectively. Root's current loader accepts the catalog including realization and type constraints. Lookup checks preserve unsupported artifact CAS, deferred CPU CAS, unknown paper fetch-old and artifact optional old values. Four elementary semantic examples and one isolated C++ address-expression example pass; these are explanation checks, not accelerator executions. The validator, source inventory and range hashes remain in the preserved campaign corpus; no binaries enter Git.
