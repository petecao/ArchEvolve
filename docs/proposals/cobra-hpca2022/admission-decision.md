# Decision proposed: v0 mapping fits, production admission awaits parent review

Use v0 for **required tuple materialization**: `operation: write`, `subtype: tuple_bin`, `execution_role: execute`, `record_kind: mapping`. `binupdate` really appends supplied tuples, and LLC drain really writes those tuples into allocated bins. This required Binning output is the exact program object represented. Hardware does not execute the later irregular update to the application's destination array. The custom subtype names the concrete write form, while result/ordering/completion fields retain the paper's scope and unknown physical release protocol.

The DRT admission decision warns against disguising task construction as read results or expanding v0 to fit a whole architecture. COBRA's tuple collection differs: the supplied pair and its materialized bin output are already identifiable writes. No new top-level operation or schema/DSL is necessary for this limited mapping. A query with a requested byte-address pattern needs evidence because C-Buffers are not byte addressable; payload type/index-width requests likewise need evidence. These uncertainties do not establish unsupported hardware, nor do they establish a deployable binding.

An unconstrained write query will retrieve a mapping reference, carrying the exact tuple output and all conditions. No scatter subtype, atomics, old-value return, arithmetic reduction, general indirect coverage or global flush visibility is asserted. Adding a generic scatter operation would conflate bin storage with destination updates. Labeling this as optional assistance would understate the required tuple output of the transformed PB program.

The precise remaining implementation gap is **consumer release for allocated tuple bins**: bind `binflush` to drained intermediate queues and outstanding bin writes, all producer cores, visibility/fences, and safe ownership/lifetime. Also recover base/offset ABI and the assumed OS VA/PA support. These are scoped source unknowns and integration obligations, not a demand for a formal DSL. They are recorded as requirements and completion limitations. If a downstream catalog consumer cannot preserve this restricted mapping meaning, defer admission rather than broaden its operation semantics.

This proposal does not alter the production catalog or grant workload legality. Parent review may admit this mapping as paper evidence or retain it in research. Application reorder/numeric correctness and runnable source remain independently gated either way.
