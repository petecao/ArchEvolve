Rows preserve the separate DX100 paper/artifact records and Terminus configurations; this is not a count of 20 unrelated microarchitectures.

“Work removed” means delegated work or memory-latency assistance, not a measured speedup. Synchronization summarizes existing catalog requirements. “Missing” means this catalog does not establish an explanation or concrete interface; it does not prove the mechanism is absent. No new implementation, numerical, or performance claims are added.

## Unit, trigger, and result paths

The rows summarize functional mappings, not complete RTL or register interfaces. Three paths below make the work-performing actor and its inputs/outputs explicit using the same cited evidence.

### DX100 access families and the pinned indirect-load path

In the paper mapping, SLD fetches constant-stride elements, ILD gathers base-plus-index elements into scratchpad slots, and RNG expands active half-open ranges into index tiles used by subsequent accesses. Software submits typed tiles, bases, and instructions through memory-mapped stores. In the pinned artifact, the indirect-load API supplies a base, index tile, result tile, and optional mask; execution reads uint32 indices, forms and range-checks addresses, then places response words into the original iteration slots. Pending packets, response counts, and modeled latency gate finish and tile-readiness publication. The CPU's `wait_ready` is a held mapped load followed by `mfence`. This describes the access path and completion accounting, not a newly established RTL block partition or every consumer/reuse barrier. [dxp-read](https://github.com/petecao/ArchEvolve/blob/d13caa7ba5aaabf551f31ddd60270591a065440e/catalog/hardware-v0.1.yaml#L726), [dxp-interface](https://github.com/petecao/ArchEvolve/blob/d13caa7ba5aaabf551f31ddd60270591a065440e/catalog/hardware-v0.1.yaml#L759), [dxc-gather](https://github.com/petecao/ArchEvolve/blob/d13caa7ba5aaabf551f31ddd60270591a065440e/catalog/hardware-v0.1.yaml#L778), [dxc-completion](https://github.com/petecao/ArchEvolve/blob/d13caa7ba5aaabf551f31ddd60270591a065440e/catalog/hardware-v0.1.yaml#L858), [dxc-reuse-scope](https://github.com/petecao/ArchEvolve/blob/d13caa7ba5aaabf551f31ddd60270591a065440e/catalog/hardware-v0.1.yaml#L1050).

### TMU Fig.8 traversal-to-callback path

The Fig.8 mapping begins with row-pointer traversal over `[0, num_rows)`. Row begin/end bounds are broadcast to two range lanes with offsets 0/1 and stride 2. Those lanes fetch column indexes and nonzero values, use the column indexes to fetch vector `b`, and LockStep-marshall paired operand vectors. GITE supplies the `ri` callback; the CPU multiplies, reduces, and accumulates its operands. GEND supplies `re`; the CPU stores the row result and resets the accumulator. TG output state machines preserve callback/operand order through the double-buffered outQ. These logical traversal and callback stages do not establish physical response tags, exact encodings, consumed acknowledgement, or final partial-chunk/drain behavior. [tmu-fig8](https://github.com/petecao/ArchEvolve/blob/d13caa7ba5aaabf551f31ddd60270591a065440e/catalog/hardware-v0.1.yaml#L1624), [tmu-cpu](https://github.com/petecao/ArchEvolve/blob/d13caa7ba5aaabf551f31ddd60270591a065440e/catalog/hardware-v0.1.yaml#L1635), [tmu-outq](https://github.com/petecao/ArchEvolve/blob/d13caa7ba5aaabf551f31ddd60270591a065440e/catalog/hardware-v0.1.yaml#L1666), [tmu-unknowns](https://github.com/petecao/ArchEvolve/blob/d13caa7ba5aaabf551f31ddd60270591a065440e/catalog/hardware-v0.1.yaml#L1728).

### ExTensor selection-to-operand path

Sequencer configuration supplies loop bounds, strides, and tensor-dimension maps; `Iterate` selects a level and parent. Scanners produce increasing coordinates and EOS. Intersect consumes matching heads together, drops the smaller unmatched head, and flushes when either stream ends. Surviving coordinate-position tuples address separate operand-data storage, and tile coordinates accompany the delivered data. The selected catalog operation is this coordinate/position and operand-delivery path, rather than a grant of scalar arithmetic or a concrete DMA/fence interface. [extensor-ordered-intersection](https://github.com/petecao/ArchEvolve/blob/d13caa7ba5aaabf551f31ddd60270591a065440e/catalog/hardware-v0.1.yaml#L2213), [extensor-coordinate-position](https://github.com/petecao/ArchEvolve/blob/d13caa7ba5aaabf551f31ddd60270591a065440e/catalog/hardware-v0.1.yaml#L2232), [extensor-partial-output](https://github.com/petecao/ArchEvolve/blob/d13caa7ba5aaabf551f31ddd60270591a065440e/catalog/hardware-v0.1.yaml#L2252).

## Prefetch assistance and required values

Prodigy, Scalar Vector Runahead, and Triangel assist memory access rather than replace the program's required-value channel. Prodigy advances a software-described indirection graph on demand loads and prefetch fills. Scalar Vector Runahead executes transient instruction copies without delivering architectural register results. Triangel replays learned address pairs to issue speculative prefetches; it does not establish a loaded-value indirection ABI. Treat their output as cache assistance, not as a returned gather value or completed update. These catalog records do not specify a programmer-visible offload-completion fence. The architectural program remains responsible for its required loads, computation, and synchronization.

## Completion and storage ownership

Required-data supply has several distinct boundaries. In MAPLE, a pointer-produce store can retire on acknowledgement before its memory reply arrives; the later consume-load response supplies the queued value. The fetched array must remain stable while that queued value is in use. TMU preserves operand/callback order and lets the CPU process one full outQ chunk while another fills, but this catalog does not establish its consumed acknowledgement, final partial-chunk delivery, or reuse protocol. COBRA's binflush sends residual tuples through the hierarchy, and all tuples must reach their memory bins before software Accumulate begins; the inspected paper does not bind this requirement to a host done/ACK/fence interface. Documentation must therefore distinguish submission acceptance, operand availability, producer drain, storage reuse, and CPU/update visibility rather than treating any one signal as universal completion.
